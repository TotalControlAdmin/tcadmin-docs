Script Events

A script event decides when a script runs, picked from the editor's Script Events list. A script can bind several at once — e.g. AfterServiceCreated and AfterServiceReinstalled.

Which events a script can bind depends on where it lives:

ScriptWhere you create itEvents it can bind
Blueprint scriptOn a game or Docker blueprintEvery applicable event on this page.
Global scriptSystem → Settings → Global Game/Docker ScriptsThe same events, for the blueprints the admin selects on the script: all of them, or one or more.
Service scriptOn a single service, by owner or adminOnly ScheduledTask, CustomServiceAction and CustomServiceIcon.

Every event gets the standard script objects — ThisService, ThisServer, ThisGame/ThisDockerBlueprint, ScriptConsole, Variables, the managers (see Script Objects). Extra variables below is what an event adds on top.

In C#, extra variables are read with Variables["Name"] or Dynamic.Name; other engines get them as ordinary globals.

note

Event names are case-sensitive. A script's Operating System setting means the OS of the hosting server, not of a container image.

Service lifecycle​

EventFires whenExtra variables
BeforeServiceCreatedBefore a new game service creates.—
AfterServiceCreatedAfter it creates and registers.—
BeforeServiceDeletedBefore deletion (also before a Docker reinstall's delete half).—
AfterServiceDeletedAfter files and registration are removed.—
BeforeServiceReinstalledBefore a game service reinstalls.—
AfterServiceReinstalledAfter a game service reinstalls.—
BeforeServiceMovedSource server, before the move (incl. host↔VS). Not fired for copies.—
AfterServiceMovedTarget server, after the moved service registers. Not fired for copies.—

Delete and move apply to game and Docker services. Create/reinstall are game-only; a Docker reinstall runs delete instead.

Power (start, stop, kill)​

These apply to game and Docker services. An After* event fires only once the action succeeds — a failed start never reaches AfterServiceStarted.

EventFires whenExtra variables
BeforeServiceStartedBefore the service is started.—
AfterServiceStartedAfter the service has started.—
BeforeServiceStoppedBefore the service is stopped.—
AfterServiceStoppedAfter the service is stopped.—
BeforeServiceKilledBefore the service process is force-killed.—
AfterServiceKilledAfter the service process is force-killed.—
note

Stop service stops the service before the script, restarts after; ignored for the events above.

Unexpected exit​

Game services only. Fires within a few seconds of a game server ending on its own — an RCON quit, a crash, an out-of-memory kill, an in-game shutdown. Stopping, killing or restarting from the panel, an OS shutdown and query-monitoring actions do not fire it. The panel also writes an Exited Unexpectedly entry to the service's activity log.

EventFires whenExtra variables
ServiceExitedUnexpectedlyAfter a running service exited without TCAdmin asking it to.ExitCode (int?), ExitReason (string?), ExitTime (DateTime, UTC), ProcessId (int), ServiceIOProcessId (int), RestartScheduled (bool)

The game blueprint's Monitoring page controls whether TCAdmin schedules an automatic restart.

warning

ExitCode is null when the panel could not read it — for example when the game was force-killed by the OS or the service helper process crashed before the code was captured. Always null-check it. ProcessId is 0 in the same case. On Windows, closing the server's console window kills the server immediately and records ExitReason = "ConsoleClosed" alongside the exit code.

Example — start the server again unless it exited cleanly (ServiceManagerService requires Run Impersonated to be unchecked on the script):

var exitCode = Variables["ExitCode"] as int?;
ScriptConsole.WriteLine(exitCode.HasValue
    ? $"Server exited with code {exitCode}"
    : "Server exited, exit code unknown");

if (exitCode != 0)
    await ServiceManagerService.StartService(ThisService.ServiceId);

Scheduled and on demand​

The only events a service script can bind, for game and Docker services.

EventFires whenExtra variables
ScheduledTaskOn the task's recurring schedule.The script's own input variables, with the values stored on the schedule.
CustomServiceActionOn clicking the script's action button.The script's own input variables, with the values the operator filled in.
CustomServiceIconWhen the panel draws the custom status icon.The script's own input variables.
VisualScriptBlockNever fires as a trigger. Publishes the script as a reusable Run Script block in the Visual Script Editor.—

Access is role-based: no roles means admin-only; otherwise a sub-user needs the per-service Script → Execute permission and a regular user needs one of the script's roles.

Mods​

Admin-curated per-blueprint mods, shared by game and Docker services. See Mods.

EventFires whenExtra variables
BeforeModInstallBefore a mod's files install.ModName (string), ModId (long), BlueprintMod (BlueprintMod)
AfterModInstallAfter install and recording.ModName, ModId, BlueprintMod
BeforeModUpdateBefore an in-place update.ModName, ModId, BlueprintMod
AfterModUpdateAfter an in-place update.ModName, ModId, BlueprintMod
BeforeModUninstallBefore tracked files are removed.ModName, ModId, BlueprintMod
AfterModUninstallAfter removal.ModName, ModId, BlueprintMod
note

Adding this makes a script only eligible — also attach it to the mod in the mod editor's Scripts list.

An in-place update needs update scripts attached; otherwise the mod fully uninstalls and reinstalls. AfterModInstall files aren't tracked, so uninstall won't remove them — pair it with an uninstall script that reverts the work.

Blueprint content sync​

Fires per blueprint, not per service — a script refreshes the blueprint's mods and game updates from an external catalog automatically.

EventFires whenExtra variables
SyncBlueprintContentDaily, per blueprint with a bound script (time set under Data Retention & Maintenance → Sync Blueprint Content), or on demand via Run sync now.ThisBlueprint, plus ThisGame (Game) or ThisDockerBlueprint (DockerBlueprint)
warning

No service in scope — ThisService is null, and so is everything derived from it. Run Impersonated and Stop service are ignored.

  • Runs on the master server — Operating System must include it. Select both if unsure.
  • A failing script logs and the pass continues. A missed day catches up in one run; a mid-run request is dropped, not queued.
  • Blueprints with no bound script are skipped.
  • New mods/updates start with no roles (admin-only) — assign roles in the script.

These variables exist only while a query-monitoring event fires — absent elsewhere (custom actions, icons, scheduled tasks, power events). For an on-demand count, call GameServiceManager.QueryService(ThisService).

Config files​

These three events let a blueprint script watch — and refuse — every config-file touch. They work for game and Docker blueprints.

EventFires whenExtra variables
BeforeServiceConfigFileReadBefore a registered config file reads. A script can deny the read.ConfigFile, ConfigFileId, ConfigFilePath, ConfigFileRelativePath, Source, UserId, ThisUser
BeforeServiceConfigFileWrittenImmediately before a registered config file writes. A script can deny the write.Same as above.
AfterServiceConfigFileWrittenAfter it lands on disk and variables sync. Never denies — already saved.Same as above.

Only registered config files​

Fires only for a config file registered on the blueprint (its Config Files tab), after path tokens expand. Everything else — logs, saves, mod files, bulk uploads — is ignored. No bound script means nothing runs.

What triggers a read​

BeforeServiceConfigFileRead fires on any of these reads (a folder download/compress does not count — it isn't per-file):

WhereAction
File ManagerOpening or downloading it.
Config Files pageOpening the raw or structured editor.
FTP / FTPSDownloading it.
SFTPDownloading it.
AI AssistantReading it.
SavingAny save — the panel reads the file first to check permissions (see note below).

What triggers a write​

The same list of surfaces fires two events: BeforeServiceConfigFileWritten immediately before the write (a script can deny it), then AfterServiceConfigFileWritten once the file is on disk and synced:

WhereAction
Config Files pageSaving either editor.
File ManagerSaving, uploading, renaming/moving onto the path, or extracting an archive containing it.
FTP / FTPS and SFTPUploading, or renaming onto its path.
Visual Script EditorA Create File block that writes it.

Available variables​

All three events also provide:

VariableTypeDescription
ConfigFileConfigFileThe matched blueprint entry — Name, Template, Editor, relative path.
ConfigFileIdlongThat entry's id.
ConfigFilePathstringThe file's full path on the hosting server.
ConfigFileRelativePathstringPath relative to the service root, forward-slashed, tokens expanded.
SourcestringWeb, Ftp or Sftp. Panel, REST API, visual editor and archive extraction all report Web.
UserIdlongThe attributed user; 0 means no user was behind it.
ThisUserUserThat user — null when UserId is 0; always null-check it.

Both come from the blueprint entry, not the caller's path, so they match regardless of surface.

Denying a read or a write​

BeforeServiceConfigFileRead and BeforeServiceConfigFileWritten refuse; AfterServiceConfigFileWritten never does — it's already saved. A bound script denies by:

  • setting Globals.ReturnValue to boolean false (reason: denied by script), or
  • failing with an error (reason: the error message).

Only a real boolean counts — "false" or 0 does not deny. With several scripts bound, a failure outranks a mere false, since its message says what actually broke.

The user sees, per surface:

SurfaceRead deniedWrite denied
Panel (File Manager, Config Files page)Reading '<file>' was denied by a script: <reason>.Saving '<file>' was denied by a script: <reason>.
FTP / FTPSA 550 reply with the reason.A 550 reply with the reason.
SFTPA permission-denied error with the reason.A permission-denied error with the reason.
warning

A save fires all three events in order. The panel reads the file first to check permissions (BeforeServiceConfigFileRead), then fires BeforeServiceConfigFileWritten immediately before writing — either can refuse: a denying read script blocks the save before anything runs, a denying write script leaves the file untouched. Only once the write and variable sync finish does AfterServiceConfigFileWritten fire, and it cannot deny.

note

Ignore Errors is how a deny gate fails open. Ticked, a crash in the script lets the read or write through instead of refusing it. It does not soften an explicit false, or cover another bound script's failure.

Notes for all three events​

  • AfterServiceConfigFileWritten never fails the operation — errors are logged on the hosting server and the file stays saved.
  • All three are awaited: a slow script slows the read/save/upload; AfterServiceConfigFileWritten always sees the final content with variables already synced.
  • Stop service behaves as for any other event — stops before the script, restarts after. Rarely wanted on a read.

Example: refuse to save a config file while the service is running​

Bind to BeforeServiceConfigFileWritten on the blueprint. Admins pass through; everyone else is refused from saving while the server runs — the point is that nobody overwrites a file the running server will clobber or reload mid-session.

info

ServiceManagerService requires the Run Impersonated option to be unchecked on the script.

//refAssemblies: TCAdmin.SDK.dll, TCAdmin.GameHosting.SDK.dll, TCAdmin.Scripting.dll, TCAdmin.Monitor.dll
using TCAdmin.SDK.Database.Entities;             // User
using TCAdmin.Web.Shared.Models.Enums;           // EServiceStatus

var Globals = new TCAdmin.Scripting.Engines.Addons.CSharpGameGlobals(); // DO NOT MODIFY THIS LINE

var relativePath = Variables["ConfigFileRelativePath"] as string;
var source = Variables["Source"] as string;

// null when the operation has no user behind it (UserId is 0) — always check.
var user = Variables["ThisUser"] as User;
var isAdmin = user != null && user.IsAdminOrTopLevelSubAdmin;

if (isAdmin)
{
    ScriptConsole.WriteLine($"Allowing {user.Username} to save '{relativePath}' via {source}.");
}
else if ((await ServiceManagerService.GetServiceStatus(ThisService.ServiceId)).Status == EServiceStatus.Started)
{
    ScriptConsole.WriteLine($"Refusing to save '{relativePath}': the server is running.");

    // Boolean false denies the write. The user is told the save was denied by a script.
    Globals.ReturnValue = false;
}

Example: restart the service after a config file changes​

Bind to AfterServiceConfigFileWritten. Logs who changed what, then restarts the service to apply the new settings.

info

ServiceManagerService requires the Run Impersonated option to be unchecked on the script.

//refAssemblies: TCAdmin.SDK.dll, TCAdmin.GameHosting.SDK.dll, TCAdmin.Scripting.dll, TCAdmin.Monitor.dll
using TCAdmin.SDK.Database.Entities;             // User
using TCAdmin.Web.Shared.Models.Enums;           // EServiceStatus

var Globals = new TCAdmin.Scripting.Engines.Addons.CSharpGameGlobals(); // DO NOT MODIFY THIS LINE

var relativePath = Variables["ConfigFileRelativePath"] as string;
var source = Variables["Source"] as string;
var user = Variables["ThisUser"] as User;
var who = user?.Username ?? "an automated task";

ScriptConsole.WriteLine($"'{relativePath}' was changed by {who} via {source}.");

// Only restart the settings file we care about.
if (relativePath == "server/cfg/server.cfg")
{
    var status = await ServiceManagerService.GetServiceStatus(ThisService.ServiceId);
    if (status.Status == EServiceStatus.Started)
    {
        ScriptConsole.WriteLine("Restarting the service to apply the new settings...");
        await ServiceManagerService.RestartService(ThisService.ServiceId);
    }
}
